## 二、后端代码骨架

```
backend/
├─ pom.xml                              # Spring Boot 3.2 / Java 17，Flyway 指向迁移目录
└─ src/
   ├─ main/
   │  ├─ java/com/gym/
   │  │  ├─ GymApplication.java         # 应用入口（含架构约定说明）
   │  │  ├─ system/                     # M0 用户权限/基础数据/审计
   │  │  ├─ membership/                 # M1+M2 会员与会籍
   │  │  ├─ course/                     # M3 课程与排课
   │  │  ├─ booking/                    # M4 预约与签到
   │  │  ├─ payment/                    # M5 收费与财务
   │  │  ├─ assessment/                 # M7 体测与数据
   │  │  ├─ warning/                    # 预警（创新点）
   │  │  ├─ equipment/                  # M6 器材与场地
   │  │  ├─ report/                     # M8 报表与工单
   │  │  └─ shared/                     # 共享内核（唯一公共依赖）
   │  │     ├─ rule/RuleEngine.java     #   规则引擎契约（SYS-R1–R10）
   │  │     ├─ event/                   #   领域事件
   │  │     ├─ audit/                   #   审计留痕
   │  │     └─ common/                  #   统一返回/错误码/分页
   │  └─ resources/application.yml      # 配置（密钥走环境变量）
   └─ test/
      ├─ java/com/gym/architecture/
      │  └─ ModuleBoundaryTest.java      # ArchUnit 架构守卫测试
      └─ resources/features/             # 行为驱动 .feature 的落地位置（第五阶段场景）
```

> 第五阶段的 `.feature` 采用**单一来源**：文件保存在 `05-测试用例与测试计划/features/`，
> 代码落地时通过 Maven 资源目录指向该处（或由构建脚本复制），避免出现两份不同步的场景文件。

## 三、模块内分层（每个业务模块同构）

```
booking/
├─ api/            # 对外契约与控制器（其他模块只能依赖这里）
│  ├─ BookingFacade.java          # 模块契约接口（已建立）
│  └─ BookingController.java      # REST 入口（仅本模块与前端交互）
├─ application/    # 用例编排、事务边界、发布领域事件
│  └─ BookingAppService.java
├─ domain/         # 领域对象、状态机、规则判定（不依赖框架与外部实现）
│  ├─ Booking.java
│  └─ BookingStateMachine.java
└─ internal/       # 基础设施实现：Repository、外部适配器
   ├─ BookingRepository.java
   └─ BookingJpaEntity.java
```

- **api**：唯一对外入口；返回 DTO，不暴露领域实体。
- **domain**：纯业务逻辑，状态迁移只能由领域方法触发。
- **internal**：实现细节，其他模块**不可依赖**。

## 四、依赖方向

```
api ──▶ application ──▶ domain ◀── internal
                          ▲
        （shared 可被全部模块依赖，shared 不依赖任何业务模块）
模块之间：只允许 A.api ← B.api（经契约或事件），禁止 B.internal、禁止直读对方表
```

**硬约束（ArchUnit 守卫，已实现）**：
1. `shared` 不依赖任何业务模块；
2. 跨模块不得依赖对方 `internal`；
3. `Controller` 不得直接依赖 `Repository`。

## 五、规范约定

| 项 | 约定 |
|---|---|
| 包名 | `com.gym.<module>.<layer>`，模块名与 M0–M8 对应 |
| 命名 | 类用 UpperCamelCase；方法/字段 lowerCamelCase；常量 UPPER_SNAKE |
| 契约 | 每个模块**只有一个**对外 Facade；契约接口在 `api` 包 |
| 规则 | 阈值不得硬编码；统一经 `RuleEngine` 读取 `rule_config` |
| 迁移 | SQL 只放 `07-数据库与部署设计/db/migrations`，按 `V{n}__描述.sql` 递增 |
| 测试 | 单元/接口/架构测试与业务代码同库；`.feature` 与需求编号绑定 |
| 提交 | `type(scope): 说明`，如 `feat(booking): 实现约课校验` |

## 六、新增切片如何接入（不破坏既有逻辑）

1. 新建（或扩展）模块包，**只新增**文件；
2. 如需使用既有能力，**只调用对方 api 契约**，不修改对方 internal；
3. 新表以新增迁移脚本（如 `V6__*.sql`）加入，不改既有列；
4. 新增行为驱动场景，绑定新需求编号；
5. 提交前跑 ArchUnit 守卫与 `.feature` 冒烟，确保边界未被破坏。
