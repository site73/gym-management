# 关键规则行为驱动测试场景（.feature）

> 所属阶段：第五阶段（测试用例与测试计划确认）
> 表达形式：Given—When—Then（Gherkin，可被 Cucumber / behave / pytest-bdd 直接执行）
> 存放位置：本目录 `features/` 下，共 5 个 .feature 文件

## 一、场景文件清单与溯源

| .feature 文件 | 覆盖规则/需求 | 场景数 | 对应用例 |
|---|---|---|---|
| features/booking.feature | SYS-R1/R2/R3；REQ-B4-001、REQ-B3-001 | 7 | TC-B4-001~006、TC-B3-001 |
| features/attendance.feature | SYS-R4；REQ-B4-002~005 | 5 | TC-B4-007~011 |
| features/membership.feature | SYS-R1/R5/R6；REQ-B1-002/004/005、REQ-B5-002/004 | 7 | TC-B5-001~004、TC-B5-002/007、TC-B1-006/007 |
| features/warning.feature | SYS-R7/R8/R9；REQ-B8-001~006、REQ-B2-001 | 8 | TC-B8-001~006、TC-B2-001/002 |
| features/commission.feature | SYS-R10；REQ-B5-005 | 3 | TC-B5-009/010 |

**合计 30 个行为驱动场景**，覆盖全部 10 条关键规则（SYS-R1–SYS-R10）。

## 二、示例（节选自 booking.feature）

```gherkin
场景: 累计爽约三次限制预约七天
  假如 会员"李四"已累计 2 次爽约
  当 该会员再次发生一次爽约
  那么 该会员爽约次数应更新为 3
  并且 系统应在 7 天内限制该会员的预约权限
```

## 三、运行方式

- 使用 Cucumber / behave / pytest-bdd 均可执行；步骤实现（step definitions）调用系统接口或服务层。
- 测试代码、.feature 文件、接口契约（OpenAPI）与系统代码**进入同一版本库**，按版本同步管理。
- 关键规则、流程、状态或接口发生变更时，相关 .feature 场景必须同步更新。
- 关键测试未通过时，不得进入试点或正式部署。

## 四、追溯关系

| 层级 | 编号 | 一对一关系 |
|---|---|---|
| 业务规则 | R1–R10 | → 系统规则 SYS-R1–R10 |
| 系统规则 | SYS-R1–R10 | → 需求 REQ-Bx-nnn |
| 需求 | REQ-Bx-nnn | → 测试场景（.feature）/ 用例 TC-Bx-nnn |

三者通过《关键规则—需求—测试溯源表》（第四阶段）与本文件建立完整追溯链，任一层变更都会传导到测试。

## 五、验收要求

- S1 切片相关场景（booking/attendance/membership）为**准入必有**：未通过不得进入集成与试点。
- warning.feature 为创新点验收依据，须其规则式判定逻辑先通过（模型演进后另行补充准确率测试）。
- commission.feature 须与财务口径核对一致后才可确认提成结果。
