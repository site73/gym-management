# 测试计划（切片版）

> 所属阶段：第五阶段（测试用例与测试计划确认）
> 上游依据：《目标系统需求分析报告》《系统规则与约束说明》《关键规则—需求—测试溯源表》
> 原则：测试用例与测试计划**在需求阶段同步形成**，不等编码完成才补写；每个业务切片形成需求后同步形成对应测试用例。

## 1. 目的与范围

- 目的：在需求确认的同时确定"怎么验"，使每条需求、每条关键规则都有可执行的验证方式，避免后期临时补测。
- 范围：覆盖切片 S1–S5 及支撑模块 M0；本轮以 S1（最小闭环）为最高优先。
- 不在范围：性能压测的详细方案（见设计阶段非功能测试）、多门店/硬件等范围外功能。

## 2. 测试来源与本计划映射

| 测试来源 | 主要落在 | 说明 |
|---|---|---|
| 业务流程路径 | 端到端/业务流程测试 | 按 B0 与板块流程（S1–S5） |
| 角色权限 | 权限测试 | 越权访问与数据可见性 |
| 业务活动 | 功能测试 | A1–A11 对应功能点 |
| 状态转移 | 状态机测试 | 五类状态机合法/非法迁移 |
| 业务规则 | 行为驱动测试 | SYS-R1–R10 |
| 决策表 | 组合/决策测试 | 爽约处理决策表等 |
| 异常处理 | 异常测试 | 支付失败、冲突、超时 |
| 输入边界 | 边界值测试 | 容量、次数、时间窗 |
| 输出结果 | 结果校验 | 提示文案、状态、金额 |
| 报表和指标 | 数据校验测试 | RP1–RP9 口径正确性 |

## 3. 测试层次

单元测试 → 接口测试 → 契约测试（OpenAPI）→ 集成测试 → 业务流程测试 → 异常测试 → 行为驱动验收测试（.feature）。各层次与需求编号、规则编号绑定追溯。

## 4. 优先级与轮次

| 轮次 | 覆盖切片 | 优先级 | 准出要求 |
|---|---|---|---|
| R1 | S1 | 最高 | S1 用例全通过，P0 缺陷清零 |
| R2 | S2 | 高 | 支付与对账用例全通过 |
| R3 | S3、S4 | 中 | 转化、提成、预警用例通过 |
| R4 | S5、M0 | 中 | 工单、报表、权限用例通过 |

## 5. 环境要求

- 开发环境、测试环境、预发环境各一套；生产环境不用于测试。
- 小程序测试号 + 微信支付**沙箱**；外部接口（登录/支付/订阅消息/短信）一律走 Mock 或沙箱（对应第六阶段原型验证）。
- 定时任务（评分、提醒、结算）需支持手动触发以便测试。

## 6. 数据要求

- 测试数据：会员、会籍（有效/冻结/过期）、课程与容量、预约与签到记录、订单、体测、工单。
- 数据须**脱敏**（手机号等），不使用真实会员数据。
- 每轮测试前重置基线数据集（seed），保证可重复。

## 7. 通过标准（准出准则）

- 关键规则（SYS-R1–R10）对应的行为驱动场景 100% 通过。
- P0 缺陷为 0，P1 缺陷关闭率 ≥ 95%。
- 核心流程（约课、签到、支付、核销）端到端通过。
- 报表指标口径抽样核对一致。

## 8. 缺陷管理

- 缺陷级别：P0（阻断核心流程）、P1（严重，无绕过方案）、P2（一般）、P3（轻微/建议）。
- 缺陷须关联需求编号与用例编号，修复后回归。

## 9. 角色与职责

- 开发：单元/接口/契约测试编写执行。
- 测试：集成/流程/异常/边界用例执行与缺陷跟踪。
- 店长/业务方：行为驱动验收测试确认（业务口径）。

## 10. 追溯与版本管理

- 用例编号 TC-<模块>-<序号> 与需求编号、规则编号双向绑定（见《测试用例集（切片版）》）。
- .feature 文件、测试代码、接口契约与代码进入同一版本库，规则变更时测试同步更新。
- 关键测试未通过不得进入试点或正式部署。

## 11. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 外部接口（支付/消息）不可用于测试 | 阻塞 S2 | 先用 Mock/沙箱，Q9/Q10 尽早关闭 |
| 预测类功能无历史数据 | 无法验证准确率 | 先验规则式（SYS-R7/R9）逻辑，模型后置 |
| 测试数据准备不足 | 覆盖不全 | 建立 seed 数据集并版本化 |
