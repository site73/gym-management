# 部署方案设计

> 所属阶段：第七阶段（数据库、外部接口、业务数据初始化与部署方案设计）
> 编排文件：`deploy/docker-compose.yml`、`deploy/nginx.conf`、`deploy/.env.example`
> 原则：可先在本机/试点跑通，再以相同编排放大到生产；部署方案与数据迁移切换安排衔接，形成完整上线方案。

## 一、运行环境

| 组件 | 版本/规格 | 说明 |
|---|---|---|
| 操作系统 | Windows 11 或 Linux | 笔记本即试点环境；生产建议 Linux |
| 容器 | Docker + Docker Compose | 一套编排，试点与生产同构 |
| 数据库 | MySQL 8.0（utf8mb4, +08:00） | 仅监听 127.0.0.1，不暴露公网 |
| 缓存/队列 | Redis 7（AOF 持久化） | 会话、access_token 缓存、定时任务锁 |
| 后端 | API 服务（容器，端口 8080） | 业务服务 + 规则引擎 + 定时任务 |
| 反向代理 | Nginx 1.27（80/443） | 强制 HTTPS、转发 API、托管管理后台 |
| 会员端 | 微信小程序 | 由微信平台承载，后端提供 API |

## 二、网络与安全要求

- **强制 HTTPS**（TLS 1.2/1.3），HTTP 301 跳转；开启 HSTS、`X-Content-Type-Options`、`X-Frame-Options`。
- 数据库与 Redis **不对外暴露端口**（compose 中绑定 `127.0.0.1`）。
- 密钥与凭据一律走 `.env`（**不入版本库**，`.gitignore` 已排除），禁止硬编码。
- 支付回调 `/api/pay/notify` 必须公网可达且**验签**；其余接口仅需小程序侧可达。
- 权限最小化：应用使用独立数据库账号（非 root），仅授予必需权限。
- ⚠️ 关联提醒：本机全局 git 配置存在 `http.sslVerify=false`，**建议改回 true** 或安装代理根证书（与部署无关，但同属本机安全基线）。

## 三、发布方式

1. **构建**：CI 或本地 `docker compose build`，镜像打标签 `gym-api:<版本号>`（对应阶段号或语义化版本）。
2. **数据库迁移**：容器启动前/启动时执行 Flyway，按 `V1→V5` 顺序回放迁移脚本，并跑 `R__seed_base_data.sql`；**迁移失败即中止发布**。
3. **部署**：`docker compose up -d`（滚动重建 API 容器）。
4. **验证**：健康检查 `/actuator/health`；冒烟关键路径（登录 → 约课 → 签到）。
5. **回滚**：镜像回退到上一标签 + 数据库回滚到发布前备份（结构变更以"只增不改"为原则，降低回滚难度）。
6. **发布窗口**：避开门店营业高峰（建议闭店后），切换类发布与数据迁移同窗口执行。

## 四、配置管理

| 配置项 | 存放位置 | 是否入库 |
|---|---|---|
| 数据库/Redis 连接、端口 | `.env` | 否（`.env.example` 入库） |
| 微信 AppID/Secret、支付商户密钥 | `.env` | 否 |
| 业务规则参数（N/D/T、时间窗、提成比例） | 数据库 `rule_config`（店长可配） | 是（不含敏感信息） |
| 运行环境标识（dev/pilot/prod） | `.env` 的 `APP_PROFILE` | 否 |

规则参数与代码解耦，改阈值无需发版，且变更留 `version` 与操作人。

## 五、日志与监控

- **应用日志**：输出到 `deploy/logs`，按天滚动，保留 30 天；关键操作写 `audit_log`（权限、状态、财务）。
- **访问日志**：Nginx 记录，保留 30 天。
- **监控指标**（初步）：接口错误率、P95 响应时间、定时任务执行结果、支付回调失败数、notification 失败数。
- **告警**：支付异常（订单 `abnormal`）、预警任务超时升级、定时任务失败、磁盘/容器异常 → 通知店长与技术负责人。

## 六、备份与恢复策略

| 项 | 策略 |
|---|---|
| 数据库备份 | 每日 02:00 `mysqldump` 全量备份到 `deploy/backup`，保留 14 天 |
| 增量保护 | 开启 binlog，支持按时间点恢复 |
| 恢复演练 | 每季度一次恢复演练，记录 RTO/RPO |
| 目标 | RTO ≤ 4 小时；RPO ≤ 24 小时（试点期可放宽） |
| 迁移前备份 | 数据迁移执行前**强制全量备份**并校验可恢复 |

## 七、试点环境与生产环境的差异

| 维度 | 试点（本机/单机 Docker） | 生产 |
|---|---|---|
| 部署 | docker compose 单机 | 同编排，建议独立服务器 + 定时快照 |
| 数据 | 测试数据或迁移演练数据（脱敏） | 真实业务数据 |
| 外部接口 | Mock / 微信沙箱 | 微信正式环境（真实商户号） |
| 域名与证书 | 自签证书或本机访问 | 正式域名 + 受信证书 |
| 备份 | 手动备份 | 自动每日备份 + 异地留存 |
| 监控告警 | 人工查看日志 | 自动告警 |

**差异原则**：试点与生产使用**同一套编排与迁移脚本**，仅配置与数据不同，避免"试点能跑、生产跑不起来"。

## 八、与数据迁移切换的衔接（上线方案）

1. **T-7**：生产环境搭建完成（MySQL/Redis/API/Nginx），执行全部迁移与种子数据，验证空库可正常启动。
2. **T-3**：试点环境完成迁移演练；生产环境做一次"演练数据"全流程验证（含支付沙箱）。
3. **T-1**：生产库全量备份 + 校验；确认回滚预案；冻结旧台账写入。
4. **T 日**：执行正式数据迁移 → 核对签字 → 开放系统；现场值守。
5. **T+3**：观察期结束，输出上线小结；关闭遗留清单。
