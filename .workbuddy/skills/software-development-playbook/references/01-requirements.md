# 01 · 需求分析

## 适用场景

- 用户给出模糊诉求（"做个管理后台""把这个流程线上化"）
- 需要在动手前把范围、边界、验收标准定下来
- 需求中途变更，需要判断影响面

## 核心原则

1. **从业务活动出发，不从页面/功能出发**：先问"谁在什么场景下要完成什么事"，再谈界面。
2. **每条需求可追溯**：需求必须能指向一个业务活动或规则，否则是"无源需求"，要砍或补依据。
3. **验收标准前置**：写需求时就写清"怎么算做完了"，不留到测试阶段补。
4. **先冻结范围，再排优先级**：范围反复变动是最大的进度风险。

## 执行步骤

### 步骤 1 · 建立业务—需求映射
1. 列业务活动（谁、何时、做什么、产出什么）。
2. 每个活动映射 1–N 条系统需求，编号（如 `REQ-<域>-<序号>`）。
3. 反向检查：每条需求都能回到某个活动/规则；每个活动都有需求落点。

**验收**：存在一张双向可查的追溯表，无"无源需求"，无"无落点活动"。

### 步骤 2 · 用 EARS 句式写需求
按场景选句式，避免"系统应友好""尽量快"这类不可验证的表述：

| 类型 | 句式 | 用于 |
|---|---|---|
| Ubiquitous | 系统应…… | 始终成立的约束 |
| Event-driven | 当……时，系统应…… | 由事件触发 |
| State-driven | 在……状态下，系统应…… | 状态相关行为 |
| Unwanted | 若……，则系统应…… | 异常与防护 |
| Optional | 在具备……的条件下，系统应…… | 可选能力 |

**验收**：每条需求能被写成一条可执行断言（输入 → 期望输出）。

### 步骤 3 · 拆边界与异常
对每条需求补四问：
1. 空值/极值/超长输入怎么办？
2. 并发或重复提交怎么办？
3. 权限不足或跨归属访问怎么办？
4. 上游失败（网络/第三方/超时）怎么办？

**验收**：异常分支有明确期望（拒绝码、提示、补偿动作），不是"待定"。

### 步骤 4 · 定优先级与切片
- 用 Must / Should / Could 分级。
- 按"能独立演示的纵向切片"排序，而不是按技术层排序。
- 每个切片要有：范围、验收标准、依赖。

**验收**：第一个切片能在一轮内跑通端到端，而不是"先做完所有表"。

### 步骤 5 · 变更影响分析
需求变更时回答三问：
1. 影响哪些已有需求/规则？
2. 影响哪些代码模块与数据？
3. 已交付的测试哪些会失效？

**验收**：变更单上写明影响面与需要回归的用例范围。

## 验收清单

- [ ] 需求编号唯一，可被测试用例引用
- [ ] 每条需求有业务依据
- [ ] 每条需求有可验证的验收标准
- [ ] 异常与权限分支已覆盖
- [ ] 切片可独立演示
- [ ] 变更影响面已评估

## 常见偏差

| 偏差 | 后果 | 纠正 |
|---|---|---|
| 直接罗列功能点 | 需求无来源，后期砍不动 | 补业务活动映射 |
| 只写正常流程 | 上线后异常路径全是 bug | 强制四问 |
| 验收标准写成"功能可用" | 无法判定完成 | 改成可执行断言 |
| 按技术层切片 | 迟迟没有可演示成果 | 改纵向切片 |

## 待验证

- EARS 句式的颗粒度：过细会导致需求条目爆炸，建议以"一个可验证行为"为一条。
