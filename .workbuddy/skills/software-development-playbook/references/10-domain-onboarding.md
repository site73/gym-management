# 10 · 新领域适配（拿到陌生业务时先做什么）

## 适用场景

- 要开发一个自己完全不熟悉的领域（库存、客户、医疗、金融、物流……）
- 只有一个模糊需求，没有领域专家全程陪同
- 已有 Skill/模板，但不确定哪些能直接套、哪些必须重新建模

## 核心原则

1. **先建"领域词典"，再谈功能**：同一个词在不同行业含义完全不同（"订单""库存""客户"）。
2. **找不变量，不找功能点**：功能会变，不变量不会（钱不能凭空产生、库存不能为负）。
3. **先找并发点，再选技术**：哪里会同时被多人/多流程改，决定了架构的难点。
4. **承认无知**：不确定的地方列成问题清单去问，不要用通用经验硬套。

## 六问清单（必须全部回答）

### Q1 术语：这个词在本领域指什么？
产出**领域术语表**，每条写：术语 / 定义 / 与相邻概念的区别 / 单位。
重点是容易混淆的三类：
- 同一词多义（"库存"是实物、可用量、还是账面值？）
- 近义词（"出库 / 发货 / 扣减"是不是一回事？）
- 隐含状态（"在途"算不算库存？）

**验收**：业务方看术语表能确认"对，就是这个意思"，且没有两个术语互相循环定义。

### Q2 状态：有哪些实体，各自的生命周期？
产出**状态清单**：实体 / 状态枚举 / 允许的迁移 / 触发条件 / 终态。

判定标准：能否画出状态机，且每条边都有触发事件？画不出说明还没理解业务。

**验收**：每个状态都有"谁会把它改到这个状态"，没有"僵尸状态"。

### Q3 不变量：什么情况绝对不允许发生？
产出**不变量清单**：编号 / 表述 / 违反后的后果 / 如何校验。

典型类型：
- 数量守恒（期初 + 入 − 出 = 期末）
- 非负约束（余额、库存、额度）
- 唯一性（同一单据不能重复入账）
- 顺序约束（先审批后执行、先付款后发货）
- 归属约束（数据只能属于一个主体）

**验收**：每条不变量都能写成一个可执行的断言，且能指出"哪段代码可能破坏它"。

### Q4 并发点：哪里会被同时修改？
产出**并发点清单**：资源 / 并发场景 / 竞争后果（超卖、重复入账、丢失更新）/ 期望语义。

判定方法：问"两个人同时点提交会怎样"；对每个写操作都问一遍。

**验收**：每个并发点都有明确的处理策略（见 `03-architecture.md` §并发与一致性）。

### Q5 集成点：依赖谁，失败怎么办？
产出**依赖清单**：外部系统 / 交互方式 / 失败影响 / 降级方案 / 是否可重试。

**验收**：每个外部依赖都有"它挂了会怎样"的答案。

### Q6 合规与审计：哪些操作必须留痕？
产出**留痕清单**：操作 / 谁可执行 / 记录什么 / 保留多久。

典型：金额变更、权限变更、状态回退、数据导出。

**验收**：监管/审计要求能映射到具体日志字段。

## 执行步骤

### 步骤 1 · 收集原始语料
不要一上来问"你要什么功能"。先要：
- 现有单据/表格/截图（最能暴露真实字段与流程）
- 岗位与职责（谁在什么时候做什么）
- 异常处理的口口相传规则（"这种情况我们一般……"）

**验收**：能列出至少 3 个真实业务场景的完整输入输出。

### 步骤 2 · 填六问清单
逐条回答 Q1–Q6，不确定的标 `待确认` 并写明找谁确认。

**验收**：六问无空白项（可以待确认，但不能没意识到）。

### 步骤 3 · 交叉验证
用三个方法验证理解是否正确：
1. **复述**：把流程讲回给业务方，看是否被纠正。
2. **反例**：举一个"系统应该拒绝"的场景，确认判断一致。
3. **边界**：问"如果是 0 / 负数 / 超大值 / 重复提交，业务上怎么处理"。

**验收**：至少被纠正过一次（没被纠正通常说明问得不够深）。

### 步骤 4 · 映射到通用能力
把领域概念映射到通用构件：

| 领域概念 | 通用构件 | 注意 |
|---|---|---|
| 单据/流水 | 事件/明细表 | 必须可追溯、不可改只能冲正 |
| 余额/库存 | 计数字段 | 必须能由明细派生（总控 R4） |
| 审批流 | 状态机 | 状态与权限绑定 |
| 对账 | 全量不变量校验 | 定期跑，差异要能定位到明细 |

**验收**：每个领域概念都有落点，没有"特殊到无法建模"的（真有则单列）。

### 步骤 5 · 产出"领域适配卡"
汇总成一张卡（用 `templates/domain-glossary.md`），作为后续需求/架构/测试的共同底稿。

**验收**：需求文档、数据模型、测试用例都能引用这张卡的编号。

## 常见误判

| 误判 | 表现 | 后果 |
|---|---|---|
| 用旧领域经验硬套 | "库存不就是个数字字段" | 忽略批次/效期/在途，后期重构 |
| 跳过术语对齐 | 开发理解的"可用量"和业务不同 | 逻辑全错但测试全绿 |
| 只问功能不问不变量 | 需求写完发现"负库存"没定义 | 上线后账实不符 |
| 忽略并发 | "内部系统没人同时用" | 高峰期超卖/重复入账 |
| 把合规当附加项 | 最后才加日志 | 审计字段缺失，无法补 |

## 验收清单

- [ ] 术语表完成，无循环定义
- [ ] 每个实体有状态机，无僵尸状态
- [ ] 不变量清单每条可断言
- [ ] 并发点有处理策略
- [ ] 外部依赖有失败方案
- [ ] 留痕要求映射到字段
- [ ] 至少被业务方纠正过一次
- [ ] 产出领域适配卡并被下游引用

## 待验证

- "至少被纠正一次"作为理解深度的代理指标，适用于复杂业务；简单 CRUD 可放宽。
