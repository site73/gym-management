# 06 · 质量控制

## 适用场景

- 需要设计测试策略、补齐测试覆盖
- 判断"能不能交付"
- 做安全与边界探测
- 建立回归防线

## 核心原则

1. **分层防御**：不同层解决不同问题，不能只靠一种测试。
2. **测试要能挡住真实事故**：每条用例对应一个曾经或可能发生的问题。
3. **可复现**：一条命令跑完，自带数据准备与复位。
4. **覆盖要有缺口清单**：不追求数字好看，如实标注未覆盖项。

## 执行步骤

### 步骤 1 · 设计测试矩阵
按层划分，每层职责单一：

| 层 | 解决什么 | 不解决什么 |
|---|---|---|
| 单元 | 规则、算法、状态迁移 | 集成问题 |
| 架构 | 依赖方向、分层约束 | 业务正确性 |
| 契约 | 接口形状、字段、错误码 | 业务规则 |
| 集成 | 真实 HTTP 全链路、权限 | 页面交互 |
| 前端静态 | 未定义函数、元素缺失、接口不存在 | 运行时行为 |
| 真实浏览器 | 点击有响应、渲染正确、无 JS 错误 | 性能 |
| 冒烟 | 核心路径可用 | 边界 |

**验收**：每层有明确职责，不重复也不遗漏。

### 步骤 2 · 建立不变量用例
对关键约束写"全量校验"，而不是抽查：
- 计数 = 明细条数（逐条遍历）
- 状态机无非法迁移
- 越权一律 403、未登录 401
- 敏感字段不出现在响应里

**验收**：不变量用例能在数据异常时立刻报警。

### 步骤 3 · 异常与边界用例
必测清单：
1. 空值 / 极值 / 超长 / 非法类型
2. 重复提交 / 并发
3. 越权（改 ID、改 scope、伪造归属）
4. 上游失败 / 超时
5. 满员 / 余额为 0 / 已取消等边界状态

**验收**：每条都有明确期望码与提示。

### 步骤 3.5 · 并发 / 幂等 / 对账测试

这三类是"功能测试全绿但生产出事"的高发区，必须单独立项。

**并发测试**

| 用例 | 做法 | 断言 |
|---|---|---|
| 同一资源并发扣减 | N 个线程/请求同时扣同一 ID | 成功数 ≤ 可扣数；最终值不为负；差值 = 成功数 |
| 并发创建同唯一键 | 同时提交相同业务键 | 只成功一条，其余返回冲突而非报错 |
| 并发状态流转 | 同时对同一单执行"通过" | 只有一次生效，其余返回状态冲突 |
| 读多写少竞争 | 一边查询一边更新 | 查询不返回中间态（或明确允许脏读） |

**要点**：并发用例容易"偶发通过"，必须多次运行（如 20 轮）并统计失败率；
断言要落在**最终数据**上，不能只看 HTTP 状态码。

**幂等测试**

| 用例 | 做法 | 断言 |
|---|---|---|
| 重复提交创建 | 同一幂等键发两次 | 返回同一业务 ID；明细只产生一条 |
| 回调重放 | 同一回调发两次 | 状态只迁移一次；副作用（如加余额）只发生一次 |
| 消息重投 | 同消息投两次 | 与上同 |
| 超时重试 | 首次超时后客户端重试 | 不产生两条记录 |

**断言要点**：不能只断言"第二次返回 200"，要断言**明细表条数与余额变化**。

**对账测试（数据一致性）**

| 类型 | 公式/方法 | 适用 |
|---|---|---|
| 期初期末平衡 | 期初 + 入 − 出 = 期末 | 库存、余额、积分 |
| 计数与明细 | 汇总字段 = 明细条数（全量遍历） | 名额、已读数、订单数 |
| 跨表勾稽 | 单据总额 = 明细金额之和 | 订单/发票 |
| 状态与金额 | 已支付金额 = 支付流水之和 | 支付 |

**要点**：
- 对账用例要**遍历全量**对象，不做抽样（抽样会漏掉出问题的那一条）。
- 差异要能**定位到明细**，只报"对不上"没有价值。
- 建议做成可重复执行的对账脚本，既能测试也能运维。

**时序测试**

- 回调乱序到达（先到"完成"后到"开始"）
- 延迟消息在状态已变更后到达
- 跨天/跨时区边界（账期、日切）

**验收**：以上四类各有至少一条用例；并发用例多次运行稳定；对账脚本可独立执行。

### 步骤 4 · 安全探测
在功能测试之外单独做一轮：
- 认证绕过（无 token、篡改 token、过期 token）
- 越权（水平/垂直）
- 注入（SQL/命令/模板）
- 输出转义（存储型 XSS）
- 回调伪造（无签名/弱校验）
- 敏感信息泄露（密码、密钥、内部路径）

**验收**：每项给出"安全/风险"结论，风险项标注级别与修复建议。

### 步骤 5 · 数据准备与隔离
- 每个用例自带前置数据，不依赖其他用例。
- 用唯一后缀（时间戳）避免多次运行冲突。
- 测试开始前复位，结束后不污染环境。

**验收**：单独跑任一用例都能通过。

### 步骤 6 · 出报告
报告包含：执行环境、用例总数与通过数、失败项根因、未覆盖项与原因、复跑命令。

**验收**：他人按报告能原样复现结果。

## 验收清单

- [ ] 测试矩阵分层清晰
- [ ] 关键不变量有全量校验
- [ ] 异常/边界/安全用例齐备
- [ ] 用例相互独立、可单跑
- [ ] 报告含复跑命令与缺口说明
- [ ] 全量一次通过或有明确解释

## 常见偏差

| 偏差 | 后果 | 纠正 |
|---|---|---|
| 只做接口测试 | 页面点了没反应照样上线 | 加静态检查 + 浏览器测试 |
| 用例互相依赖 | 顺序一变就挂 | 自带数据 + 复位 |
| 只测正常路径 | 异常全漏 | 强制清单 |
| 追求覆盖率数字 | 覆盖了但没断言 | 看断言质量 |

## 待验证

- 真实浏览器测试的稳定性依赖环境（浏览器版本、等待策略），需按项目固化。
