# 04 · 开发执行

## 适用场景

- 需求与设计已定，进入编码
- 在既有代码里加功能或改造
- 需要控制改动风险、保证可回滚

## 核心原则

1. **小步提交**：一次提交只做一件可描述的事，便于回滚与定位。
2. **跟随既有风格**：命名、分层、异常处理先看邻居怎么写，不引入第二套风格。
3. **先跑通再优化**：正确性优先，性能与抽象留到有证据时再做。
4. **不留半成品**：要么完整实现（含异常分支），要么用开关隔离，不要留"临时凑合"。

## 执行步骤

### 步骤 1 · 读上下文（总控 R1）
1. 找到要改的文件与它的调用方/被调用方。
2. 看同一模块内相似功能怎么写的。
3. 确认数据流：入口参数 → 校验 → 业务 → 持久化 → 返回。

**验收**：能口述这次改动的完整数据流与影响面。

### 步骤 2 · 拆任务
按"可独立验证"拆：
- 数据层（迁移/实体）
- 契约层（接口/DTO）
- 业务层（规则）
- 入口层（接口/页面）
- 测试

**验收**：每个子任务完成后系统仍可运行（不留中间不可用状态）。

### 步骤 3 · 实现（按顺序）
1. 先写数据与契约（形状定下来）。
2. 再写业务规则（核心逻辑）。
3. 最后接入入口（Controller/页面）。
4. 每层加最小验证（单测或手测）。

**验收**：每层都有对应验证，不把全部验证压到最后。

### 步骤 4 · 处理异常与边界
强制覆盖：
- 参数为空/越界/类型错
- 重复提交/并发
- 权限不足/跨归属
- 上游超时/失败
- 数据不存在

**验收**：每个分支有明确返回（码 + 提示），无 500 裸奔。

### 步骤 5 · 自测
1. 正常路径跑通。
2. 逐个异常分支验证。
3. 用极值数据（超长名、0 条、满员）验证展示与逻辑。

**验收**：自测记录可复现，不依赖"我觉得没问题"。

### 步骤 6 · 提交
- 一次提交一个主题，消息写"做了什么 + 为什么"。
- 提交前检查：无调试代码、无临时文件、无真实密钥（总控 R8）。
- 大改动拆多个提交，保证任一提交可构建。

**验收**：`git log` 能读懂演进过程；任一提交可回滚且不破坏构建。

## 验收清单

- [ ] 改动跟随既有风格
- [ ] 分层完整，未跨层调用
- [ ] 异常与边界分支已实现
- [ ] 自测覆盖正常 + 异常 + 极值
- [ ] 提交粒度合理、消息清晰
- [ ] 无调试残留与敏感信息

## 常见偏差

| 偏差 | 后果 | 纠正 |
|---|---|---|
| 一次改十几个文件 | 出问题无法定位 | 拆小步 |
| 只写正常路径 | 上线即爆 | 强制异常清单 |
| 引入新框架/新风格 | 维护成本翻倍 | 跟随既有约定 |
| 调试代码混进提交 | 泄露或行为异常 | 提交前 grep |

## 待验证

- "每层最小验证"的具体形式（单测/契约测试/手工）需按项目测试基建决定。
