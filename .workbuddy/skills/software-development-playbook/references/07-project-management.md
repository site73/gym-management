# 07 · 项目管理与上下文

## 适用场景

- 多步任务需要持续推进
- 会话中断、上下文丢失，需要接手
- 需要向他人汇报进度或交接
- 任务范围蔓延，需要收敛

## 核心原则

1. **状态外置**：进度写在文件/任务清单里，不依赖记忆。
2. **断点可续**：任何时刻中断，下一个会话都能接上。
3. **范围可见**：做什么、不做什么、何时做，写清楚。
4. **风险前置**：把"可能挡住交付"的事尽早暴露。

## 执行步骤

### 步骤 1 · 建立任务清单
把目标拆成可验证的条目，每条含：
- 动词开头的标题（"实现 X""修复 Y"）
- 验收标准
- 依赖关系
- 当前状态

**验收**：任一时刻能回答"现在做到哪、下一步是什么"。

### 步骤 1.5 · 制定开发计划

任务清单回答"做什么"，计划回答"按什么顺序、什么时候能交"。用 `templates/development-plan.md`。

**计划必须包含**：

| 要素 | 要求 |
|---|---|
| 里程碑 | 每个里程碑有可演示的产出（不是"完成 60%"） |
| 依赖 | 标出"谁挡谁"，识别关键路径 |
| 风险 | 每条风险有触发信号与应对 |
| 缓冲 | 关键路径末端留缓冲，不平均分配 |
| 验收人 | 每个里程碑谁验收 |

**排期方法**：
1. 先排关键路径（最长依赖链），它是工期下限。
2. 可并行的任务并行，但标注共享资源冲突。
3. 把"不确定最大"的任务往前排——早失败比晚失败便宜。
4. 预留缓冲（经验值：关键路径的 15%–20%，按团队熟悉度调整）。

**里程碑设计原则**：
- 每个里程碑都能**端到端演示**一条完整链路，而不是"数据库建完了"。
- 第一个里程碑尽量小（1–2 周），用来验证技术选型与协作方式。

**验收**：计划表能回答"如果今天开始，第三周能演示什么""哪个环节延期会拖累整体"。

### 步骤 2 · 维护上下文文件
在项目里固定位置维护一份"当前状态"，包含：

```
## 当前进度
- 已完成：…
- 进行中：…
- 下一步：…
## 关键决策
- 决策：… / 理由：… / 代价：…
## 环境事实
- 启动命令、端口、账号、依赖版本
## 已知风险
- 风险：… / 影响：… / 缓解：…
```

**验收**：新人只读这个文件就能接手。

### 步骤 3 · 阶段汇报
每完成一个阶段，输出三句话：
1. 做了什么（结果，不是过程）
2. 验证了什么（命令/测试/现象）
3. 还差什么（风险与下一步）

**验收**：汇报不含"正在进行中"这类无法验证的表述。

### 步骤 4 · 控制范围蔓延
出现新需求时：
1. 记录到"候选项"，不立即插入当前迭代。
2. 评估影响（工期/风险/依赖）。
3. 与用户确认优先级后再排。

**验收**：当前迭代范围有明确边界，新增项有去处。

### 步骤 5 · 交接
交接包含：项目结构、运行方式、账号、当前状态、未完成项、坑与注意事项、关键文件索引。

**验收**：接手方能在 30 分钟内跑起来并定位到关键代码。

## 上下文管理技巧

| 场景 | 做法 |
|---|---|
| 大仓库探索 | 先按文件名/关键字搜索，再定向读，不整目录通读 |
| 长文件 | 分段读，先看结构（标题/类/函数签名） |
| 多轮修改 | 每轮结束复述"改了什么、为什么"，防止漂移 |
| 会话重置 | 关键信息落盘，不依赖对话记忆 |
| 信息冲突 | 以代码/日志为准，文档冲突时标注并修正 |

## 验收清单

- [ ] 任务清单状态准确
- [ ] 上下文文件存在且最新
- [ ] 每阶段有可验证汇报
- [ ] 新增需求有候选项与优先级
- [ ] 交接材料完整

## 常见偏差

| 偏差 | 后果 | 纠正 |
|---|---|---|
| 进度只记在脑子里 | 会话一断就重来 | 落盘 |
| 边做边加需求 | 永远交付不了 | 候选项机制 |
| 汇报讲过程不讲结果 | 无法判断是否完成 | 只讲结果与验证 |
| 不写环境事实 | 换机就起不来 | 固化到文档 |

## 待验证

- 上下文文件的位置与命名需按团队约定；单项目建议放仓库根目录并纳入版本管理。
