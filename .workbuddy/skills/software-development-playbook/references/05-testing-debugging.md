# 05 · 测试与调试

## 适用场景

- 启动失败、连接失败、超时、乱码
- 功能结果与预期不符
- 偶发失败、时好时坏
- 需要定位"到底哪一层错了"

## 核心原则

1. **先看事实，再猜原因**：端口、进程、版本、编码、路径、日志，先确认。
2. **一次只改一个变量**：同时改三处，即使好了也不知道为什么。
3. **能复现才算定位**：无法复现的"修复"不可信。
4. **修完必须防回归**：见总控 R3。

## 执行步骤

### 步骤 1 · 界定故障边界
问四个问题：
1. 是所有请求都失败，还是特定接口？
2. 是所有环境都失败，还是只有本机？
3. 是一直失败，还是偶发？
4. 最近改了什么？

**验收**：能把故障缩小到"某一层/某一条件"。

### 步骤 2 · 环境事实核对（总控 R6）
按顺序检查并记录输出：

| 检查项 | 命令/方式 | 期望 |
|---|---|---|
| 进程是否存在 | 进程列表 | 目标进程在 |
| 端口是否监听 | 端口查询 | 目标端口 LISTENING |
| 依赖服务 | 连通性测试 | 可连接 |
| 版本/编码 | 版本命令、日志 | 与预期一致 |
| 代理/环境变量 | 环境变量 | 不劫持本地访问 |
| 路径/权限 | 列目录、写测试 | 可读写 |

**验收**：能指出"哪个事实不成立"，附命令输出。

### 步骤 3 · 按层缩小
从外到内逐层验证：
1. 网络/端口
2. 入口（请求是否到达、参数是否正确）
3. 业务（规则是否按预期分支）
4. 持久化（SQL/数据是否正确）
5. 返回（序列化/前端渲染）

**验收**：定位到具体层与具体行，而不是"后端有问题"。

### 步骤 4 · 读日志的正确姿势
- 先看第一条 ERROR（后面的常是连锁反应）。
- 看异常链的 `Caused by`。
- 对照时间点，确认与操作对应。
- 关注"启动阶段"与"首次调用"的差异。

**验收**：能引用具体日志行说明根因。

### 步骤 5 · 构造最小复现
1. 去掉无关步骤，保留能触发故障的最短路径。
2. 固定随机因素（时间、ID、顺序）。
3. 写成脚本或测试，便于反复执行。

**验收**：同一输入必现同一结果。

### 步骤 6 · 修复与验证
1. 先写失败用例。
2. 改最小范围。
3. 用例转绿。
4. 跑相关模块全量测试，确认无连带影响。
5. 回滚验证：撤掉修复后用例应再次失败。

**验收**：修复点可解释因果；回归用例进入套件。

## 偶发问题专项

| 现象 | 常见根因 | 处理 |
|---|---|---|
| 首次调用失败、后续正常 | 冷启动/懒加载/连接池预热 | 预热或加重试 |
| 约 1/3 概率失败 | 测试间数据耦合、执行顺序依赖 | 每个用例自带数据准备与复位 |
| 时快时慢 | 外部依赖抖动、锁竞争 | 加超时与隔离 |
| 只在某台机器失败 | 环境变量/编码/路径差异 | 固化环境或显式声明 |

**验收**：偶发问题能给出触发条件，并有稳定复现手段。

## 验收清单

- [ ] 故障已缩小到具体层
- [ ] 环境事实有命令输出佐证
- [ ] 有最小复现
- [ ] 根因可解释（因果链完整）
- [ ] 回归用例已加入套件
- [ ] 相关模块全量通过

## 常见偏差

| 偏差 | 后果 | 纠正 |
|---|---|---|
| 一上来改代码 | 越改越乱 | 先核对事实 |
| 同时改多处 | 无法归因 | 单变量 |
| 只看最后一条报错 | 错过真正根因 | 看第一处 Caused by |
| 修完不写用例 | 下次同样问题再来 | 强制 R3 |

## 待验证

- 各技术栈的"冷启动预热"手段不同，需按栈确认。
