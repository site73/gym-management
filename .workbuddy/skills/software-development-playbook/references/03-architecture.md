# 03 · 架构设计

## 适用场景

- 新系统选型（单体 / 模块化单体 / 微服务）
- 已有系统分层混乱、改一处崩三处
- 需要做数据建模与边界划分
- 需要为技术决策留档（ADR）

## 核心原则

1. **架构服务于团队与交付节奏**，不是追最新范式。小团队、边界未清 → 模块化单体。
2. **边界靠机制守，不靠自觉**：模块依赖方向要有自动化检查（如 ArchUnit）。
3. **契约先行**：跨模块只依赖接口/DTO，不依赖实现与实体。
4. **每个决策都有代价**：写清"放弃了什么"，否则无法复盘。
5. **可逆性优先**：优先选容易改回去的方案。

## 执行步骤

### 步骤 1 · 划边界（限界上下文）
1. 按业务能力分组（不是按技术层）。
2. 每组一个模块，模块内高内聚，模块间低耦合。
3. 明确每个模块的对外契约（能给别人什么）。

**验收**：能画出一张模块依赖图，箭头单向、无环。

### 步骤 2 · 选形态并写明理由
| 形态 | 适用 | 不适用 |
|---|---|---|
| 单体 | 早期、团队小、边界不清 | 需要独立扩缩容 |
| 模块化单体 | 边界清晰但部署统一 | 团队规模大到需要独立发布 |
| 微服务 | 多团队、独立发布、独立扩容 | 小团队、强一致事务多 |
| 事件驱动 | 松耦合、异步流程 | 强一致、需要同步结果 |

**验收**：ADR 中写明"为什么不是另一个"，以及未来什么信号出现时该迁移。

### 步骤 3 · 定分层与依赖方向
典型分层：入口（Controller/Handler）→ 应用服务（用例编排）→ 领域（实体/规则）→ 基础设施（持久化/外部）。
硬约束：
- 入口层不得直连持久化。
- 跨模块只能依赖对方 api 包。
- 公共能力（日志/审计/异常）单向被依赖。

**验收**：有自动化边界测试；故意违反时测试会红。

### 步骤 3.5 · 并发与一致性

任何会被并发修改的资源（余额、库存、名额、额度、序列号）都必须先定策略，再写代码。

**先识别，再选型**（识别方法见 `10-domain-onboarding.md` Q4）：

| 场景 | 竞争后果 | 推荐策略 |
|---|---|---|
| 扣减但有下限（库存、余额） | 超卖 / 负值 | **条件更新**：`update ... set n = n - 1 where n >= 1`，以影响行数判断成败 |
| 整行编辑，冲突少 | 丢失更新 | **乐观锁**：`version` 字段 + `where version = ?` |
| 冲突频繁、事务短 | 重试成本高 | **悲观锁**：`select ... for update` |
| 跨服务/跨库 | 单库锁失效 | 分布式锁 / 单点串行化（慎用，优先改设计避免） |
| 只追加不修改（流水） | 无竞争 | 无需锁，靠唯一键防重 |

**硬约束**：
- 计数不能用"先查再改"（`select` 后 `update`），必须在一条语句里判断。
- 锁的粒度要写清（锁行 / 锁表 / 锁资源 ID），并说明持锁时长。
- 加锁失败必须有明确的用户可见结果（重试 / 排队 / 拒绝），不能静默失败。

**幂等设计**（重复提交、回调重放、消息重投）：

| 手段 | 适用 | 实现要点 |
|---|---|---|
| 幂等键 | 创建类操作（下单、入库单） | 客户端或服务端生成唯一键，唯一索引兜底 |
| 状态机幂等 | 状态流转类 | 只有"当前状态允许"才执行，重复请求直接返回既有结果 |
| 去重表 | 回调、消息 | 记录已处理的业务 ID + 时间窗口 |
| 业务唯一约束 | 天然唯一（同一单据同一明细） | 数据库唯一索引，冲突即视为已处理 |

**验收**：
- 每个写操作都能回答"同一请求来两次会怎样"。
- 并发场景有测试（见 `06-quality-control.md` 并发测试）。
- 幂等实现不依赖"前端按钮禁用"。

### 步骤 4 · 数据建模
1. 先定实体与关系，再定表。
2. 明确主键、唯一约束、外键/索引、状态字段取值。
3. 计数字段必须能由明细派生（见总控 R4）。
4. 结构变更一律走版本化迁移脚本，禁止手工改库。

**验收**：能回答"这个数从哪来、怎么校验它对不对"。

### 步骤 5 · 写 ADR
每个关键决策一份：背景 → 选项 → 决定 → 代价 → 何时重审。
关键决策包括：形态选型、数据库、鉴权方式、同步/异步、缓存策略、第三方依赖。

**验收**：新人读 ADR 能理解"为什么是这样"，而不是只知道"是这样"。

### 步骤 6 · 失败模式分析
对每个外部依赖问：
1. 它挂了会怎样？
2. 超时/重试/幂等怎么处理？
3. 数据不一致时以谁为准？

**验收**：关键链路有降级或明确失败提示，不出现静默卡死。

## 验收清单

- [ ] 模块依赖图无环、方向清晰
- [ ] 形态选型有 ADR，含"为什么不选另一个"
- [ ] 分层约束有自动化测试
- [ ] 数据模型有约束与迁移脚本
- [ ] 计数类字段可派生/可对账
- [ ] 外部依赖有失败策略

## 常见偏差

| 偏差 | 后果 | 纠正 |
|---|---|---|
| 一上来就微服务 | 运维成本压垮进度 | 先模块化单体 |
| 边界只写在文档里 | 半年后依赖成网 | 加架构测试 |
| 跨模块直接用对方实体 | 改表就崩 | 只依赖 DTO |
| 手工改数据库 | 环境间不一致 | 版本化迁移 |
