# 案例 03 · 权限边界：前端藏按钮 ≠ 权限控制

> **来源项目**：健身房运营管理系统（5 种角色：会员 / 教练 / 店长 / 管理员 / 超级管理员）
> **对应规则**：总控 R5（权限在服务端强制）
> **性质**：设计决策 + 真实攻击探测结果

## 背景

系统有 5 类角色，且同一份数据（课表、名单、账号）不同角色可见范围不同。
最直接的诱惑是"前端按角色隐藏菜单/按钮"，实现快、演示效果好。

项目明确否定这种做法：**隐藏只是体验优化，鉴权必须在服务端**。

## 设计决策

### 作用域参数由会话决定
课表接口接受 `scope`、`memberId`、`coachId`，但服务端会按当前会话**改写**：

| 角色 | 传入 | 服务端归一化为 |
|---|---|---|
| 会员 | `scope=all` | `mine` + 会话绑定的 memberId |
| 会员 | `memberId=他人ID` | 会话绑定的 memberId |
| 教练 | `scope=all&coachId=他人` | `mine` + 会话绑定的 coachId |
| 店长/管理员 | 任意筛选 | 保留（本身有全店权限） |

关键点：**归一化发生在业务层，不在 Controller 的 if 判断里**，
这样任何新入口复用同一套逻辑，不会漏。

### 垂直权限用统一入口校验
- 账号管理接口：`requireSuperAdmin()`
- 财务/排课：`requireStaff()`
- 会员自助：`requireMember()` 并取会话 memberId

## 攻击探测（真实执行）

用脚本模拟越权，实际结果：

| 探测 | 期望 | 实际 |
|---|---|---|
| 会员伪造 `memberId` 选课 | 改写为本人 | 改写为本人 ✅ |
| 会员伪造 `memberId` 约场地 | 改写为本人 | 改写为本人 ✅ |
| 教练调排课接口 | 403 | 403 ✅ |
| 教练看非本人课程名单 | 403 | 403 ✅ |
| 教练伪造 `coachId` 看他人课表 | 只返回本人 | `scope=mine` ✅ |
| 管理员访问超管账号接口 | 403 | 403 ✅ |
| 会员查看他人会员档案 | 403 | 403 ✅ |
| 篡改 token | 401 | 401 ✅ |
| 未登录访问业务接口 | 401 | 401 ✅ |
| 超管账号接口是否泄露密码 | 不泄露 | 无 password 字段 ✅ |

全部通过。这组探测后来固化成独立的 `security-probe.js`，作为回归资产。

## 一个反直觉的取舍：不提供"查看明文密码"

用户提出"超级管理员能不能看到所有人的密码"。

结论是**不能，而且不应该能**：密码以 BCrypt 单向哈希存储，系统里根本没有明文。
需求改为「重置密码」——重置为默认值并**当场把新密码返回给操作者**，同时写审计日志。

这样既满足"管理员要能掌握凭据"的真实需要，又没有破坏"密码不可逆"的安全前提。

> 这条后来写进了答辩 PPT，成为被追问时的加分点：**拒绝一个看似方便的功能，是因为它会让全站失守。**

## 同时发现的问题（已修）

权限正确不代表安全。探测还发现：

- **存储型 XSS**：自助注册的姓名 `<img src=x onerror=alert(1)>` 原样入库，
  名单弹窗未转义 → 门店打开即执行。修复：统一 `safe()` 转义所有用户可控输入。
- **支付回调无验签**：任何人知道订单号且金额对上，就能伪造"已支付"。
  列为上线前 P0 缺口（未在 mock 阶段实现验签，但如实标注）。

## 可迁移结论

1. **前端隐藏是 UX，不是安全**；判断标准：绕过前端直接调接口，能不能拿到数据？
2. **作用域归一化放在业务层**，不要散落在各个 Controller；否则新增入口必漏。
3. **权限要能被攻击验证**，不能只靠"我写了 if"。把越权探测做成可重复执行的脚本。
4. **安全设计要能解释"为什么不"**：拒绝一个功能时给出代价分析，比单纯说"不安全"更有说服力。
5. 权限正确 ≠ 安全：还要查注入、XSS、回调伪造、敏感字段泄露。
