# 案例 07 · 可运行级迁移验证（并发扣减 / 幂等 / 对账）

> **验证目的**：上一轮（案例 06）只做到"纸面推演"，本案例把它升级为**可执行证据**
> **技术栈**：Python 3.13 + SQLite（与源项目 Spring Boot + MySQL 完全不同）
> **结论**：10 项断言全部通过；Skill 给出的三条规则可直接落成代码

## 一、为什么还要做这次验证

案例 06 证明了"能产出正确的设计与计划"，但有一个自我欺骗的风险：
**规则写得对，不等于照着规则能写出对的代码。**

所以本次只做一件事：把库存系统最核心的三条规则写成可运行的最小实现，
用真实并发去打，看规则是否真的成立。

## 二、被测的三条规则

| 规则来源 | 规则 | 本案例的验证形式 |
|---|---|---|
| `03` 步骤 3.5 | 扣减用条件更新，不用"先查再改" | 两种实现对照跑 20 并发 |
| `03` 步骤 3.5 | 重复提交用幂等键 + 唯一索引 | 串行 5 次 / 并发 10 次同单号 |
| `06` 步骤 3.5 | 期初 + 入 − 出 = 期末，全量对账 | 对账平衡 + 篡改检测 |

## 三、实验与结果

### 实验 1 · 错误实现：先查再改

```sql
-- 读到的快照 → 在应用层算好 → 绝对值写回
SELECT qty FROM sku WHERE id = ?;
-- 应用层：target = 读到值 - 扣减量；中间还有别的校验（本实验用 10ms 睡眠模拟）
UPDATE sku SET qty = ? WHERE id = ?;      -- 写的是 target
```

**20 线程各扣 10，初始 100：**

| 指标 | 结果 |
|---|---|
| 成功次数 | 20 |
| 实际卖出 | 200 件 |
| 账面剩余 | 90 |
| 对账差异 | 1 个 SKU |

**超卖 100 件，且账面完全没反映。** 这就是"先查再改"在生产中的样子：
请求都返回成功，账面对不上才发现。

### 实验 2 · 正确实现：条件更新

```sql
UPDATE sku SET qty = qty - ?
WHERE id = ? AND qty >= ?;      -- 判断与扣减在同一条语句，由数据库保证原子
-- 影响行数 = 0 → 库存不足
```

**同样 20 线程各扣 10，初始 100：**

| 指标 | 结果 |
|---|---|
| 成功 | 10 |
| 失败（库存不足） | 10 |
| 异常 | 0 |
| 最终库存 | 0 |
| 对账差异 | 0 |

### 实验 3 · 幂等入库

同一业务单号提交多次，幂等键为 `INBOUND:{单号}`，靠主键唯一性保证只入账一次。

| 场景 | 首次入账 | 库存 | 流水条数 |
|---|---|---|---|
| 串行提交 5 次 | 1 | 10 | 1 |
| 并发提交 10 次 | 1 | 10 | 1 |

**注意断言写法**：不能只断言"第二次返回成功"，必须断言**库存与流水条数**——
返回成功但账多记一次，是最隐蔽的重复入账。

### 实验 4 · 对账

| 场景 | 结果 |
|---|---|
| 期初 100 + 入 80 − 出 35 | 期末 145，差异 0 |
| 故意改账面 −5（不写流水） | 对账发现 1 个差异，期望值 145，实际 140 |

对账不仅能发现"对不上"，还能给出**差异定位**（哪个 SKU、账面多少、应为多少）。

## 四、实现过程中踩的坑（也是可迁移经验）

**现象**：20 线程并发写 SQLite，19 个报
`sqlite3.OperationalError: attempt to write a readonly database`。

**排查**（按 `05` 的步骤）：
1. 单线程执行正常 → 不是权限/路径问题。
2. 只在并发时出现 → 定位到连接与事务层。
3. 检查 journal 模式：初始化时设 `PRAGMA journal_mode=WAL`，
   多连接同时首次写入需要访问 `-shm` 共享内存文件，在本机环境下失败。

**处理**：改用 `PRAGMA journal_mode=DELETE`（默认日志模式）+ `busy_timeout` +
锁冲突退避重试。改完 20 并发 0 异常。

**可迁移结论**：
- "只在并发时出现"的错误，先怀疑**连接/事务/日志模式的初始化竞争**，不是业务逻辑。
- 换存储引擎时，"并发写入"的语义差异比 SQL 语法差异更容易坑人。
- 重试要区分错误类型：只对"锁冲突/忙"重试，其它错误直接抛，否则会把真 bug 重试成幽灵问题。

## 五、这次验证证明了什么

1. **规则可执行**：三条规则都落成了代码，且用真实并发验证有效。
2. **对照有效**：错误实现不是臆想——它确实超卖了 100 件，对账确实发现了差异。
3. **技术栈无关**：全部用 Python + SQLite 实现，与源项目的 Java/Spring/MySQL 无任何复用。
4. **断言比实现更重要**：如果只断言 HTTP 200，两种实现都会"通过"；
   断言最终库存、成功次数、流水条数，才抓得住问题。

## 六、仍然没覆盖的

| 项 | 说明 |
|---|---|
| 分布式并发 | 单机 SQLite 无法模拟多节点竞争，需真实数据库或分布式锁 |
| 事务隔离级别 | SQLite 与 MySQL 的隔离语义不同，结论需在目标库上复核 |
| 性能 | 本实验只验证正确性，未测吞吐与锁等待时间 |

这些已在 `SKILL.md` §10 标为待验证，不冒充已验证。

## 七、复现方式

代码随 Skill 一起存放（不依赖任何第三方库）：

```
examples/migration-test-inventory/
├── inventory.py   # 表结构 + 三种实现（naive / CAS / 幂等入库）+ 对账
└── verify.py      # 四组实验，输出 PASS/FAIL 与 report.md
```

运行：

```bash
cd examples/migration-test-inventory
python verify.py
```

只用标准库（`sqlite3` / `threading`），无第三方依赖，任意 Python 3.9+ 可跑。
