# 案例 01 · 计数与明细不一致（名单 15/15 却查不到人）

> **来源项目**：健身房运营管理系统（Spring Boot 3 + MySQL 8）
> **对应规则**：总控 R4（计数必须有明细支撑）
> **性质**：真实事故，已修复并加回归用例

## 背景

系统有一门"瑜伽"课，容量 15。课程卡片显示 `已约 15/15（满员）`，但门店后台点开
「查看名单」，弹窗显示 **共 0 人**。

这是用户（课程设计答辩者）验收时发现的，原话是：

> "像这种已经满员的课程，他的名单不应该是共 0 人，应 15 个人满员了，
> 名单中就该有 15 个用户，那么会员的数据库中就应该存在这些。逻辑应该严格闭包。"

## 现象

| 观察点 | 实际 |
|---|---|
| 课程卡余位 | 15 / 15（满员） |
| 名单弹窗 | 共 0 人 |
| 数据库 `course.booked_count` | 15 |
| 数据库 `booking` 表中该课记录 | 0 条 |

## 根因

**两个数据源，从未对齐**：

- 余位来自 `course.booked_count`（一个被直接写死的计数字段）
- 名单来自 `booking` 表（明细）

种子脚本为了让演示"看起来满员"，直接把 `booked_count` 设为 15，
但没有插入对应的 15 条预约记录。于是账实不符。

更深一层：`booked_count` 既被当作"余额"用（条件更新 `where booked_count < capacity`），
又被当作"展示值"用，但它没有强制的派生关系，任何绕过 `occupySeat/releaseSeat`
的写入路径都会让它漂移。

## 处理

### 第一步：让演示数据有真实会员
新增迁移，插入 20 个演示会员（`member.source='demo'`，编号 M101–M120），
各带有效年卡。没有真实会员，名单补不出来。

### 第二步：补齐明细并全量重算
在启动对齐器里加 `alignRoster()`：

1. 对 3 门演示课，比较 `min(booked_count, capacity)` 与有效预约数。
2. 差额从演示会员池补 `booking` 行（已开课记为 `checked_in`，未开课记为 `booked`）。
3. **收口**：对**所有**课程执行
   `update course set booked_count = (select count(*) from booking where ... status in ('booked','checked_in'))`。

### 第三步：统一名单口径
名单接口排除 `cancelled`，使"共 N 人"与余位同口径；取消记录仍留在库中可追溯。

### 第四步：加不变量用例
新增一条集成用例：遍历**所有**课程，断言 `名单条数 == booked_count`。
首次运行检查了 59 门课，全部闭合。

## 结果

```
C001 动感单车  19/20  名单 19 人
C002 瑜伽      15/15  名单 15 人
C003 搏击操     6/12  名单 6 人
```

## 可迁移结论

1. **任何"计数"字段都必须能由明细派生**；不能派生的，必须有全量对账。
2. **演示/种子数据也要满足业务不变量**，"为了好看"写死的数字是最隐蔽的技术债。
3. 修复这类问题要**同时做三件事**：补数据、改口径、加不变量用例。
   只补数据不加用例，下次换个入口又会漂移。
4. 不变量用例要**全量遍历**而不是抽查——抽查恰好跳过了那门课，问题就会漏网。

## 反例（当时的错误做法）

修复前曾试图只改展示："名单为空时显示'暂无数据'并隐藏人数"。
这是在掩盖账实不符，用户当场否掉了——正确做法是让数据变对，不是让显示变模糊。
