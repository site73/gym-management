# 案例 05 · 交付与版本管理（34 次提交、3 个标签、两次推送失败）

> **来源项目**：健身房运营管理系统
> **对应规则**：总控 R7（交付物可被直接用）、R8（对外产物先自查元数据）、R10（收敛前跑全量）
> **性质**：真实交付过程

## 背景

项目从需求文档一路做到可运行系统 + 388 项测试 + 29 页答辩 PPT，
全部提交到 GitHub 单一仓库。整个过程 34 次提交、3 个版本标签。

## 一、提交粒度：按"主题"拆，不按"文件"拆

典型一次迭代拆成三次提交：

```
fix(booking): 报名名单与课程余位严格闭合（BUG-017 严重）
test(closure): 数据闭合回归用例（集成 +12、浏览器 +4）
docs(requirements): 新增 REQ-B4-009 数据闭合需求，测试文档同步 388 项口径
```

**为什么这样拆**：
- 回滚时能只撤修复、保留测试（或反之）；
- review 时能分开看"改了什么"和"怎么验证"；
- 历史读起来是"问题 → 验证 → 定稿"的叙事，而不是一堆文件变更。

**反例**：早期有过一次提交同时改代码、测试、文档、PPT，出问题无法单独回滚。

## 二、版本标签：附注标签写清验收口径

```
v2.1-timetable  课表式管理 + 超级管理员账号治理      374 项全绿
v2.2-closure    报名名单与课程余位严格闭合          388 项全绿
v2.3-skill      项目级技能入库                       —
```

**要点**：
- 用附注标签（`git tag -a`）而不是轻量标签，因为要写说明。
- 标签说明里写"这次交付了什么 + 多少项验收通过"，日后能直接对照。
- 标签只打在验收通过的提交上。

## 三、署名与脱敏（真实踩过的坑）

用户明确要求：**交付物中不得出现真实姓名**，统一使用 GitHub 用户名
`<username>` 与 `<username>@users.noreply.github.com`。

执行动作：
1. 新建/接管仓库先检查 `git config user.name / user.email`。
2. 提交前核对 `git log --format='%an %ae %cn %ce'`。
3. 文档、注释、README 里的署名同样替换。

**更难的一步**：如果历史提交里已经有真名，需要改写历史：

```bash
git filter-branch --env-filter '
  export GIT_AUTHOR_NAME="<username>"
  export GIT_AUTHOR_EMAIL="<email>"
  export GIT_COMMITTER_NAME="<username>"
  export GIT_COMMITTER_EMAIL="<email>"
' -- --all
# 然后清理引用并 gc
```

**复核时不能只看 `git log`**：已 gc 但仍被其他 ref 引用的旧对象会漏掉，
要遍历所有 commit 对象逐个检查。搜索真名时用完整姓名，单个汉字会误报大量常用词。

## 四、两次推送失败的处理

### 第一次：代理 502
```
fatal: unable to access '...': CONNECT tunnel failed, response 502
```
环境注入了 HTTP 代理，代理本身不可用。处理：清空代理走直连
```bash
git -c http.proxy= -c https.proxy= push origin main
```

### 第二次：直连超时
```
fatal: Failed to connect to github.com:443 after 21025 ms
```
清空代理后直连也被重置。这不是配置错误，是网络环境问题。

**处理原则**：
1. 确认本地提交完整（`git status -sb` 看 ahead 数量）——**代码不会因为推不上去而丢失**。
2. 不要在失败后改 remote、强推、或重建仓库。
3. 网络恢复后重试；标签推送失败同样重试（本次第 2 次成功）。
4. 推送成功后用 `git ls-remote origin main` 核对远程指向正确提交。

**如果 ls-remote 也因网络失败**：以 `push` 的成功输出（`old..new main -> main`）为准，
并如实告知用户"远程已更新，但当前无法再次查询确认"。

## 五、交付文档的双格式

用户要求文档同时给 `.md` 与 `.docx`。原因：
- `.md` 便于版本管理与 diff；
- `.docx` 便于直接提交/打印/评审。

做法：以 Markdown 为唯一源，用脚本转 docx，避免两份内容漂移。

**教训（图片类）**：某些 md→docx 工具对相对路径的图片不嵌入，
必须写成本地绝对路径；否则 docx 里只剩 alt 文本。

## 六、演示材料也要"可复现"

答辩 PPT 不是手工拖出来的，而是用脚本生成（含版面溢出自检），
讲稿里有逐页台词、演示步骤、时间分配、**以及时间不够时的删减方案**。

**为什么写删减方案**：内容一定比时间多。不预先设计删减，现场只能靠加快语速，
而语速一快，重点就讲不清。删减方案要标明"必讲页"和"可跳页"。

## 可迁移结论

1. **按主题拆提交**，让历史成为可读的决策记录。
2. **附注标签写验收口径**，让"这个版本能不能用"一目了然。
3. **对外身份要在第一次提交前定好**，事后改历史成本高且有风险。
4. **推送失败是网络问题，不是代码问题**：先确认本地完整，再重试，不要动仓库结构。
5. **文档单一源、多格式派生**，避免版本漂移。
6. **演示材料要有删减方案**，时间管理是交付的一部分。
