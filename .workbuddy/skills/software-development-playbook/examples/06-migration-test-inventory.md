# 案例 06 · 迁移能力验证：用本 Skill 从零设计一个库存管理系统

> **验证目的**：证明本 Skill 不依赖"健身房/课程/预约"这一套业务背景
> **验证方式**：假定只拿到 `SKILL.md` + `references/` + `templates/`，
> 没有任何原项目代码与业务知识，从零走一遍完整流程
> **结论**：首次推演暴露 9 处缺口，已全部修复；修复后六项能力全部可落地

---

## 一、测试设定

- **目标领域**：轻量库存管理系统（多仓、SKU、批次/效期、入库、出库、调拨、盘点）
- **与源项目差异**：源项目是"人—课—预约"的时段资源模型；
  本领域是"物—数量—流水"的守恒模型，无角色时段概念，核心是数量准确与并发扣减
- **约束**：不得复用源项目的业务代码、表结构、规则参数

---

## 二、六项能力逐项推演

### 能力 1：能否识别新项目的需求缺口？

**按 Skill 走的路径**：`10-domain-onboarding.md` 六问 → `01-requirements.md` 步骤 0/1/3。

**识别的隐含需求**（不是用户直接说的）：

| 隐含需求 | 来源 | 为什么容易漏 |
|---|---|---|
| 不允许负库存 | Q3 不变量 | 用户只说"能出库"，没说"出不了怎么办" |
| 可用库存 ≠ 账面库存（要扣已锁定未出库） | Q1 术语 | 两个"库存"混用，实现完才发现口径不同 |
| 批次/效期先进先出 | Q3/Q1 | 快消/医药行业必需，通用模板里没有 |
| 在途库存是否计入 | Q1 | 采购在途与仓内实物是两回事 |
| 盘点差异要留痕且可追溯 | Q6 合规 | 用户通常只说"能盘点" |
| 同一单据重复提交不能重复入账 | Q4 并发点 | 网络重试场景，用户不会主动提 |

**结论**：✅ 可以识别。关键增量是 Q1 术语与 Q3 不变量——这两个清单把"用户没说但必须有的规则"逼出来了。
**修复前**：01 只有"空值/并发/权限/上游"四问，识别不出"数量守恒""批次效期"这类领域不变量 → 已补步骤 0。

---

### 能力 2：能否独立完成架构设计？

**按 Skill 走的路径**：`03-architecture.md` 步骤 1–6（含新增的 3.5 并发与一致性）。

**产出的关键决策**：

| 决策 | 选择 | 依据（来自 Skill） |
|---|---|---|
| 形态 | 模块化单体 | 步骤 2 表：团队小、边界清晰、无需独立扩缩容 |
| 边界 | 商品 / 库存 / 入库 / 出库 / 盘点 / 报表 | 步骤 1：按业务能力分组 |
| 分层 | 入口 → 应用 → 领域 → 持久化 | 步骤 3 |
| 库存量存储 | 计数字段 + 流水表，计数字段由流水派生 | 总控 R4 + 步骤 4 |
| 并发扣减 | 条件更新（`where qty >= n`），影响行数判成败 | 步骤 3.5 表第 1 行 |
| 重复入库 | 幂等键（单据号）+ 唯一索引 | 步骤 3.5 幂等表 |
| 对账 | 期初 + 入 − 出 = 期末，全量校验 | 步骤 3.5 + 06 对账 |

**结论**：✅ 可以。`步骤 3.5` 是本次验证新增的——修复前 03 只有一句泛泛的"失败模式分析"，
无法指导"超卖怎么防"，只能靠个人经验 → 已补并发策略表与幂等设计。

### 能力 3：能否制定开发计划？

**按 Skill 走的路径**：`07-project-management.md` 步骤 1.5 + `templates/development-plan.md`。

**产出的里程碑**：

| 里程碑 | 可演示内容 | 周次 |
|---|---|---|
| M1 | 单仓入库→出库→查库存，端到端跑通 | 第 2 周 |
| M2 | 多仓 + 调拨 + 批次，主流程闭环 | 第 4 周 |
| M3 | 盘点 + 差异处理 + 权限 | 第 5 周 |
| M4 | 并发/幂等/对账测试通过 + 文档 | 第 6 周 |
| M5 | 期初导入 + 可部署 + 交接 | 第 7 周 |

关键路径：M1 → M2 → M4 → M5（M3 可与 M2 部分并行）。
最不确定项："批次效期与现有单据模型是否兼容"已前移到 M1 验证。

**结论**：✅ 可以。**修复前缺计划模板**，只能列任务清单，回答不了"第三周能演示什么" → 已补 `templates/development-plan.md` 与步骤 1.5。

### 能力 4：能否处理开发中的问题？

**按 Skill 走的路径**：`05-testing-debugging.md` 步骤 1–6。

**模拟的问题与处理**：

| 问题 | 现象 | 按 Skill 的定位路径 |
|---|---|---|
| 并发超卖 | 压测时库存变负 | 步骤 1 界定"只在并发时出现" → 步骤 3 定位到持久化层 → 检查是否用了"先查再改" |
| 重复入库 | 重试后多了一条入库单 | 步骤 1 界定"重试场景" → 检查幂等键与唯一索引 |
| 账面与实物不符 | 用户报"系统显示 10，实际 8" | 步骤 3 按层缩小 → 跑对账脚本（06）定位到具体流水 |
| 期初导入重复 | 重跑脚本后数量翻倍 | 步骤 6 修复 + 导入脚本改幂等 |

**结论**：✅ 可以。但**修复前 05 缺少"数据不一致类问题"的专门路径**（只有通用的分层缩小），
已在对账测试中补齐"差异定位到明细"的方法。

---

### 能力 5：能否进行测试和质量控制？

**按 Skill 走的路径**：`06-quality-control.md` 步骤 1–6（含新增 3.5）。

**产出的测试矩阵**：

| 层 | 本项目的具体内容 |
|---|---|
| 单元 | 数量守恒、负库存拒绝、批次先进先出 |
| 架构 | 库存模块不得直连出入库模块内部 |
| 集成 | 入库→出库→查询全链路、越权 |
| 并发 | 20 线程扣同一 SKU，断言最终值 = 初始 − 成功数 |
| 幂等 | 同一单据提交两次，断言明细只 1 条 |
| 对账 | 遍历所有 SKU：期初+入−出=期末 |
| 安全 | 越权改他人仓库、导出接口鉴权 |

**结论**：✅ 可以。**修复前缺并发/幂等/对账三类用例设计**，只有"计数=明细"一条不变量，
不足以覆盖"超卖"和"重复入账" → 已补 3.5 节（四类测试 + 断言要点 + 多次运行要求）。

### 能力 6：能否完成交付？

**按 Skill 走的路径**：`08-delivery.md` 步骤 1–6（含新增 2.5 业务数据初始化）。

**交付清单要点**：
- 结构迁移（空库可建）
- **期初库存导入 + 与台账核对**（新增）
- 规则参数（安全库存阈值、效期预警天数）
- 账号与最小权限
- 发版清单 + 回滚点
- 运行手册（含"库存对不上怎么排查"）

**结论**：✅ 可以。**修复前 08 只覆盖"结构迁移"，漏了"业务期初数据"**——
库存系统上线没有期初数据等于不能用 → 已补步骤 2.5。

| # | 缺口 | 影响 | 修复 |
|---|---|---|---|
| 1 | 无"从零做新系统"路由入口 | 不知道先做什么 | SKILL.md §3 增加入口 |

| 5 | 架构缺幂等设计 | 重复入账 | 03 步骤 3.5 幂等表 |

## 四、复验

修复后按同一路径重走：

- 六问 → 领域适配卡（术语 8 条、状态 5 个、不变量 6 条、并发点 4 个）→ 全部有模板可填
- 架构决策 7 项，每项都能指向 03 的具体步骤
- 里程碑 5 个，每个都有可演示内容与验收人
- 测试 7 层，其中并发/幂等/对账有明确断言
- 交付 9 项检查，含期初导入与对账

**结论**：六项能力全部可落地，未再发现"必须依赖源项目背景"的环节。

## 五、剩余风险（如实标注）

| 风险 | 说明 | 建议 |
|---|---|---|
| 领域适配深度依赖提问质量 | 六问能覆盖常见类型，但强监管行业（医疗/金融）还需补充合规清单 | 按行业增量补 `references/10` 的 Q6 |
| 并发测试的工程实现因栈而异 | Skill 给的是设计与断言，不是现成代码 | 按栈补脚本模板（待验证） |
| 前端/交互方法偏后台系统 | B 端表单/列表覆盖较好，C 端体验设计较弱 | 如做 C 端需扩展 `02` |

## 六、这次验证本身的方法论

1. **迁移测试要用"陌生领域 + 只给 Skill"**，否则会不自觉地用回原项目经验。
2. **卡点要记录"我当时想做什么、Skill 里找不到什么"**，这比事后评价更有价值。
3. **缺口修复要落到具体章节**，不能只加一句"注意事项"。
4. **复验不是重读，是按同一路径再走一遍**，看是否还需要外部知识兜底。
