# 软件交付实战手册 · 总控

把「用户的一句话诉求」推进到「可运行、可验证、可交付、可追溯」的结果。
本文件只放**路由、硬规则、门禁、边界**；细节一律下沉到 `references/`。

---

## 1. 三层结构

```
总控（本文件）        判断任务类型、调度模块、控制质量、兜底
  ↓
八个领域模块           需求 / 产品 / 架构 / 开发 / 测试 / 质量 / 项目 / 交付
  ↓
知识沉淀层             真实案例、踩坑、决策规则、模板
```

对应目录：

| 层 | 位置 | 内容 |
|---|---|---|
| 总控 | `SKILL.md` | 触发条件、任务路由、硬规则、门禁、边界 |
| 方法 | `references/01~08-*.md` | 每个阶段的方法、步骤、验收、反例 |
| 元方法 | `references/09-distillation.md` | 如何从项目里提炼经验、如何判定通用 vs 专属 |
| 模板 | `templates/*.md` | 需求卡、ADR、测试计划、缺陷、发版清单、交接 |
| 案例 | `examples/*.md` | 真实项目的决策、踩坑、修复全过程 |

**加载原则**：先读本文件做路由，只加载当前任务需要的 1–2 个 reference；
不要一次性把所有 reference 读进上下文。案例在遇到同类问题时按需查阅。

## 2. 触发条件

满足任一即加载本 Skill：

- 接手、重启、排查一个已有项目（"这个项目跑不起来 / 我不熟这个仓库"）
- 推进一个功能从需求到交付（"把这个功能做了"）
- 修缺陷、补测试、做回归（"再测一遍 / 有没有漏洞 / 修一下这个 bug"）
- 准备发版与交付（"上传 git / 打包 / 写文档 / 做答辩材料"）
- 复盘与沉淀（"总结经验 / 提炼成 skill / 以后怎么避免"）

不适用：纯咨询问答、一次性脚本、与本 Skill 无关的领域问题。

## 4. 十条硬规则

每条都来自真实事故，违反过就出过问题。**编号用于在评审与复盘中引用。**

### R1 先读后写
- **场景**：修改任何已有代码、配置、文档前。
- **做法**：先读目标文件与它的调用方；确认命名、分层、错误处理风格后再动手。
- **验收**：能说出"改这里会影响哪 2–3 个地方"；改动未破坏既有约定。

### R2 一次只改一个可验证的点
- **场景**：一次任务包含多个改动。
- **做法**：拆成可独立验证的小步，每步可运行/可测试；避免"大爆炸式"重写。
- **验收**：每一步都有明确的观察结果（接口返回、页面表现、测试通过）。

### R3 修缺陷必须带回归用例
- **场景**：修复任何非平凡缺陷。
- **做法**：先写能复现的用例（红），再修（绿），用例留在测试集里。
- **验收**：回滚修复后用例会失败；用例进入自动化套件而非一次性脚本。

### R4 计数必须有明细支撑
- **场景**：任何"数量/余位/统计"字段（库存、名额、余额、已读数）。
- **做法**：计数字段要么由明细派生，要么有全量对账校验；禁止只写死数字。
- **验收**：存在一条全量不变量检查（如 `count == 明细条数`），且能一键跑。

### R5 权限在服务端强制
- **场景**：多角色 / 多租户 / 数据归属。
- **做法**：作用域参数（scope、ownerId、tenantId）由服务端按会话归一化，
  不信任前端传值；越权返回 403，未登录 401。
- **验收**：构造越权参数（改 ID、改 scope）拿不到他人数据，且有用例覆盖。

### R6 环境事实先验证，再归因
- **场景**：启动失败、连不上、超时、乱码。
- **做法**：先确认端口、进程、版本、编码、代理、路径这些**事实**，
  再猜代码问题；把验证命令和输出记录下来。
- **验收**：能给出"哪个事实不成立"的具体证据，而不是"可能是环境问题"。

### R7 交付物要能被下一个人直接用
- **场景**：文档、报告、演示材料、交接。
- **做法**：同时给可读版与可编辑版（如 md + docx / pptx + 讲稿）；
  附运行命令、账号、复现步骤。
- **验收**：换一个人按文档能在 30 分钟内跑起来。

### R8 对外产物先自查元数据
- **场景**：git 提交、发布、文档署名。
- **做法**：检查提交作者、文件里的姓名/邮箱/密钥；用统一对外身份。
- **验收**：`git log --format='%an %ae %cn %ce'` 全部符合约定，无敏感信息。

### R9 不确定就标注，不编造
- **场景**：历史决策、未读过的文件、无法验证的行为。
- **做法**：写"待验证"并说明验证方式；不把推测写成事实。
- **验收**：报告中每个结论都能指向代码/日志/文档/命令输出。

### R10 收敛前跑全量
- **场景**：一次迭代结束、发版前。
- **做法**：跑完整测试矩阵（不只跑改动的部分），再更新文档与版本号。
- **验收**：全量结果全绿或失败项有明确说明与责任人。

## 5. 质量门禁（DoD）

一个阶段/一次交付只有全部满足才算完成：

| 门禁 | 判据 |
|---|---|
| 可运行 | 有明确启动命令，冷启动成功 |
| 可验证 | 关键路径有自动化或可复现的手工步骤 |
| 无回归 | 全量测试通过；失败项已解释 |
| 数据自洽 | 计数与明细闭合；状态机无非法迁移 |
| 权限正确 | 越权用例通过；敏感字段不外泄 |
| 可追溯 | 需求编号 → 代码 → 测试 → 文档可互相定位 |
| 可交接 | 有 README/运行手册/账号表 |
| 干净 | 工作区无残留调试代码、临时文件、真实密钥 |

任一项不满足，不得宣称"完成"。

## 6. 上下文管理

- **落盘优先于记忆**：关键决策、环境事实、账号、命令写进项目文档，
  不依赖对话历史（会话会重置）。
- **最小充分上下文**：只读完成任务所需的文件；大仓库先搜后读，
  不要整目录通读。
- **状态可视化**：多步任务维护任务清单，完成一项立刻更新状态。
- **断点可续**：长任务在关键节点写"当前进度 / 下一步 / 已知风险"，
  让下一个会话能接着干。
- **案例化**：踩过的坑写成"现象 → 根因 → 处理 → 如何预防"，而不是只记结论。

## 7. 自主执行与授权边界

| 类别 | 默认 | 说明 |
|---|---|---|
| 读文件、搜索、分析 | 自主 | 不需确认 |
| 本地写代码/文档、跑测试 | 自主 | 在项目目录内 |
| 本地启动服务、占端口 | 自主 | 注意不要占用系统关键端口 |
| git commit（本地） | 自主 | 提交前自查 R8 |
| git push / 发版 / 打标签 | **先确认** | 涉及外部可见性；用户明确要求时可直接执行 |
| 删除/覆盖用户数据 | **必须确认** | 先备份、列清单、小批量 |
| 生产环境/线上数据 | **必须确认** | 不做未授权的写操作 |
| 共享网盘/项目盘写入 | **必须确认** | 先下载最新版、改完给 diff、确认后再上传 |

**判断原则**：可逆、局部、只影响本机的 → 自主；
不可逆、对外可见、影响他人数据的 → 确认。

## 8. 与其它 Skill 的关系

| Skill | 负责 | 与本 Skill 的组合方式 |
|---|---|---|
| `software-engineering-lifecycle` | 业务建模与九阶段流程编排 | 它定"做哪几步"，本 Skill 定"每步怎么算做对" |
| 领域专用 Skill（如某系统的运维手册） | 该项目的环境、命令、账号 | 本 Skill 给通用纪律，项目 Skill 给具体事实 |

冲突时：**项目 Skill 的事实优先，本 Skill 的纪律不破**。

## 9. 快速开始

1. 读 §3 路由表，确定主模块。
2. 加载对应 `references/NN-*.md`。
3. 按该模块的"执行步骤"推进，每步对照"验收标准"。
4. 阶段结束对照 §5 门禁。
5. 遇到同类历史问题，查 `examples/`。
6. 需要产出物，套 `templates/`。
7. 全部完成后，按 `09-distillation.md` 把新经验写回案例库。

- 新增规则前先问：它是否在至少一个真实事故中成立？否则不进 §4。
