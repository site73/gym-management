# 业务反馈与持续迭代机制

> 所属阶段：第九阶段（代码实现、测试、试点运行、实际部署与持续迭代）
> 目标：形成"**业务 → 需求 → 实现 → 运行 → 反馈**"的持续循环

## 一、反馈渠道

| 渠道 | 面向 | 频率 | 负责人 |
|---|---|---|---|
| 系统内一键反馈（小程序/后台） | 会员、一线员工 | 随时 | 自动汇总 |
| 每日站会 5 分钟问题收集 | 店长、会籍、私教 | 每日 | 店长 |
| 每周业务例会 | 门店运营 | 每周 | 店长 |
| 运行数据看板（RP1–RP9） | 运营决策 | 每日/每周 | 店长 |
| 缺陷与需求清单（Issue） | 技术 | 随时 | 技术负责人 |

## 二、运行数据采集（与报表口径一致）

- **业务指标**：新增会员、续费率、流失率、爽约率、体验转化率、课消与提成。
- **系统指标**：约课成功率、签到成功率、支付异常订单数、提醒送达率、接口错误率、P95 响应时间。
- **使用指标**：小程序活跃、后台各角色使用频次（用于判断功能是否真的被使用）。

## 三、问题分类与流转（对应模板的"回到哪一环"）

| 问题类型 | 现象示例 | 回到 | 处理 |
|---|---|---|---|
| 业务理解问题 | 流程与实际不符、术语不对 | 《业务分析报告》 | 修订业务模型 → 升版基线 |
| 需求问题 | 缺少候补入口、限制无法解除 | 《目标系统需求分析报告》 | 修订需求 → 同步 `.feature` |
| 设计问题 | 提示不清晰、页面缺字段 | 设计阶段（UI/接口/数据） | 修订设计 → 评估影响 |
| 代码问题 | 逻辑错误、异常未处理 | 代码实现 | 修复 + 补回归测试 |
| 数据问题 | 口径不一致、迁移差异 | 数据设计 / 迁移方案 | 修口径、修脚本 |
| 环境问题 | 部署失败、性能不足 | 部署方案 | 调整配置或容量 |

## 四、迭代节奏与规则

- **迭代周期**：2 周一个迭代，每迭代交付至少一个可验证切片增量。
- **准入**：迭代项必须能追溯到业务活动/规则编号（REQ/SYS-R），否则不排期。
- **准出**：关键 `.feature` 全通过 + 无 P0/P1 缺陷，方可进入试点或发布。
- **基线演进**：涉及业务规则参数（N/D/T、时间窗、提成比例）的调整，只改 `rule_config` 并**递增 version**，不改代码、不发版；涉及业务事实的调整走基线升版（V1.0 → V1.1…）。
- **契约变更**：按《模块接口契约》的变更流程执行，破坏性变更须升版本并保留过渡期。

## 七、闭环确认

本机制使每个迭代都产生"**业务反馈 → 需求修订 → 实现 → 运行数据 → 再反馈**"的闭环；
原型验证（第六阶段）与本次代码实现测试（第九阶段）均为该闭环中已实际发生的一轮，可作为后续迭代的模板复用。
